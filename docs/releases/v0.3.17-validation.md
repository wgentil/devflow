## Initial Windows timing failure and unchanged-source retry

The first Windows Python 3.11 attempt ran all 920 tests with one failure and one
error. `test_offline_hook_shares_fixture_checks` explicitly exceeded the unchanged
five-second worker deadline (5,281 ms). The transport success-case fixture raised
a generic required-context preparation error; its original nested reason was not
printed and is not asserted known. The [initial failed report](v0.3.17-evidence/initial-windows-3.11-failed.json),
[log](v0.3.17-evidence/initial-windows-3.11-failed.log) and
[initial run status](v0.3.17-evidence/initial-ci-run.json) remain retained.

A controlled owned worker with a 5.5-second startup delay reproduced exactly the
same two failing cases on unchanged source; the other three cases passed. The
[negative reproduction](v0.3.17-evidence/controlled-startup-reproduction.json)
and [log](v0.3.17-evidence/controlled-startup-reproduction.log) are intentionally
failing diagnostic evidence, not release acceptance. The production guard stopped
workers as designed. Native startup-versus-composition cost was not separately
measured; the experiment does not establish the hidden native transport reason.

Only the failed Windows 3.11 job was rerun once on a fresh runner, using the same
candidate commit, tests, deadlines and package fingerprint. That rerun passed all
920 cases with the expected four POSIX skips. The other eight successful jobs
were retained. No test, assertion or runtime budget was changed to get a passing
run. The final CI matrix above therefore combines actual successful executions
on identical source, with the first failure preserved rather than hidden.

Known limitation: these two fixture success paths are sensitive to the default
worker wall-clock budget under slow/contended startup or execution. A future test-
harness improvement can separate content/transport assertions from speed checks;
no such change is included here, and no universal latency guarantee is made.
